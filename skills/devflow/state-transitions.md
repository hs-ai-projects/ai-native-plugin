# 飞书任务字段与状态流转

流程只看任务上这两个自定义字段：

| 字段 | 取值 | 谁在管 |
|---|---|---|
| `任务类型` | 需求 / BUG / PBC | 提单人 |
| `状态` | 待评审 / Intenting / 待开发 / 进行中 / 待验证 / 已解决 / 拒绝 | 流程回写 |

`任务类型` + `状态` 决定入口；`状态` 是**流转的唯一依据**。

## 状态流转

`任务类型` = `需求`：

```
待评审 ──进 intent 阶段──────────▶ Intenting
Intenting ──Gate A 通过─────────▶ 待开发
待开发 ──Gate B 通过、开始写码───▶ 进行中
进行中 ──提交 MR / 推分支────────▶ 待验证
待验证 ──test-verifier PASS─────▶ 已解决 并 关闭任务
被需求人驳回─────────▶ 拒绝
```

`任务类型` = `BUG` / `PBC`：**没有 intent 阶段**，是否过 Gate B 取决于 DISCOVER
判定的复杂度（判定标准见 `skills/devflow/bug-triage.md`）：

```
FAST_BUG：
待评审 ──DISCOVER 判完 FAST、开始写码──▶ 进行中
进行中 ──提交 MR / 推分支───────────▶ 待验证
待验证 ──test-verifier PASS────────▶ 已解决 并 关闭任务
被驳回────────────────────────▶ 拒绝

STANDARD_BUG：
待评审 ──DISCOVER 判完 STANDARD、建 Spec+Plan──▶（仍是 待评审，等 Gate B）
（待评审）──Gate B 通过、开始写码─────────────▶ 进行中
进行中 ──提交 MR / 推分支────────────────────▶ 待验证
待验证 ──test-verifier PASS─────────────────▶ 已解决 并 关闭任务
被需求人驳回──────────────────────────────▶ 拒绝
```

- 需求任务第一跃迁（`待评审 → Intenting`）在**进入 intent 阶段时**回写，见
  `skills/devflow/intent.md` 第 2 节；其余归主上下文，在对应 Gate / 动作完成的当口回写。
- `FAST_BUG` 没有中间跃迁，`待评审 → 进行中` 由主上下文在 DISCOVER 判完、
  开始写码时一次性回写。
- `STANDARD_BUG` 没有 `Intenting`/`待开发` 两个中间态（那是需求类任务 intent
  阶段的产物），但**要过 Gate B**——建 Spec+Plan 后停在「待评审」不变，
  Gate B 通过才一次性回写 `待评审 → 进行中`。
- 无飞书任务链接（口述需求）→ 不涉及任何状态回写，此节不适用。
- 改任务字段时**只改 `状态` 一个**，不碰 `任务类型` / 负责人 / 截止时间。
