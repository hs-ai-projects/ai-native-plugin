# 测试小组：收敛测试用例

Plan 阶段起草「验证方式」节前，用安全测试、白盒测试两个独立视角补全测试用例，
防止主上下文一人凭 AC 想当然写漏边界。FEATURE / STANDARD_BUG 通用；`FAST_BUG`
没有 Plan 文档，不适用。

何时读本文件：见 `skills/devflow/plan.md` 第4节「验证方式」。任务拆分
（Task Card）已定稿之后、写验证方式正文之前。

## 1. 豁免判据（先判，不是所有任务都要派）

主上下文在读完 Task Card 后自行判断，**不新派 agent 论证是否需要判据本身**：

- 改动**无外部输入面/权限面**（不涉及接口入参、鉴权、状态机跃迁）→ 跳过
  `security-tester`。
- 改动**分支/条件组合极少**（如纯文案改动、单一 if 判断）→ 跳过
  `whitebox-tester`，主上下文按 AC 直接写验证方式。
- 两条都命中（如纯 UI 文案 bug）→ 整个测试小组跳过，退回现状（主上下文直接
  写验证方式），不因为「有这个 skill」就强行套用。

## 2. 派发方式：并行独立扫描，不组队、不讨论

`security-tester` 与 `whitebox-tester` 各自独立扫描同一份 Spec/代码，两者
分工按坐标系区分（安全角色管接口/权限攻击面，白盒角色管代码分支，见各自
agent 文件），正常情况下不产生分歧——只有「扫描是否完整」这一个问题，用
并行派发 + 主上下文核对合并解决，不组建 team、不用 SendMessage 往返讨论
（这与 `spec.md` 第4节 Author/Reviewer 讨论组不同：那里存在真实的对抗与
仲裁需求，这里没有）。少数情况下两人对同一 AC 的预期结果理解不同（AC/Spec
原文本身有歧义），各自 agent 文件里有对应的自查与标注规则，最终汇总到第 3
节的分歧清单，由主上下文判断。

用 Agent 工具并行派发命中的角色，各自拿到同一份输入：

- **Spec 全文 + AC 清单**：各角色自己 `docs +fetch --as bot` 读，不接受主
  上下文转述——独立性要求同项目其余 agent。
- **9 面边界清单**（覆盖基线，复用 `spec-reviewer.md` 已有定义）：空数据 /
  进行中 / 失败 / 无权限 / 额度不足 / 超限 / 重复提交 / 不可逆操作 / 与现有
  同类功能是否一致。
- `whitebox-tester` 额外按场景取证据，见 `agents/whitebox-tester.md` 的
  场景区分（FEATURE 与 STANDARD_BUG 取证方式不同）。

## 3. 合并方式：主上下文直接做，不新派角色

两名角色各自的候选用例清单直接回喂主上下文；主上下文按 `TC-xx` 编号去重、
合并重叠项——**每一条去重/合并都必须留一句理由**（为什么判定是重复而不是
两条不同用例），防止静默丢用例（这是唯一需要留痕的裁决点）。不新派一个
「测试 leader」agent 做这一步：去重合并是机械核对，主上下文直接做，比再
派一个 agent 转述两份清单更省。

两名角色标注的分歧清单（同一 AC 预期结果理解不同）单独处理，不与去重混为
一谈：

- 分歧标注为**已由某一方按 Spec 原文订正**的 → 直接采用订正后的版本。
- 分歧标注为**AC/Spec 原文本身有歧义**的 → 主上下文判断是否需要回 Spec
  补一句澄清，或在测试用例里按更严格的一种读法先行记录并标注该 AC 存在
  歧义，两种处置均需在最终清单里注明，不能悄悄择一。

## 4. 产出契约

结构化表格，供 `test-verifier` 在 VERIFY 阶段直接消费：

| TC-xx | 关联 AC/Task Card | 类型 | 前置条件 | 输入 | 预期结果 | 建议验证层级 |
|---|---|---|---|---|---|---|
| TC-01 | AC-02 | 功能/白盒边界/安全 | 数据准备方式 + 是否需要 mock 外部依赖 | … | … | L1-L5（见 `agents/verifier.md`） |

**前置条件字段写作要求**：必须包含数据准备方式与是否需要 mock 外部依赖，
不能只写「是/否」——这类环境隔离信息不会自然出现在「预期结果」里，若不
显式要求就等于把判断丢给 `test-verifier` 执行时自己猜。

## 5. 升级路径

某角色发现 Spec 本身有遗漏（某条边界 Spec 未定义预期行为、无法推断）→
不能自己编预期结果，标记为 Open Item 随清单一起回喂主上下文；主上下文判断
是否需要回 Spec 补一条 AC，或仅在测试里如实记录未定义，不由角色自行决定
产品行为。

## 6. 落位

测试小组不新建文档。主上下文把合并后的清单整合进 Plan「验证方式」节正文
（执笔仍在主上下文），命令/结果描述按 `plan.md` 原有要求补全，不写「确保
正常」这类空话。

## 7. 修改边界

- 不跑测试——执行是 `test-verifier` 在 VERIFY 阶段的职责，这里只设计用例。
- 不改 Spec/AC 本身、不写实现代码、不裁决产品/业务规则。
- 不为凑齐"讨论组"形式而强行组队——本 skill 的机制核心是「豁免判据 + 并行
  独立扫描 + 主上下文合并」，不是 named agent team。
