# 观测云告警分诊 owl-alert-triage

## 本 skill 的边界（先读这条）

本 skill 是**入口适配器**，只做三件事：

**识别告警 → 解析成结构化字段 → 交给项目分诊**

**不重复取证流程**。时间窗、日志查询、前后端判断、转交数据排查——这些一律属于
**项目级分诊 skill**（如 `triage-issue`），它们才知道该项目有哪些服务、哪些库、
哪些 sub-skill。本 skill 抄一遍只会抄成空壳，且日后必然与项目侧漂移。

> 判据：本文件中**不应出现**任何具体项目名、服务名、库名、人员 open_id。
> 一旦出现，说明职责越界了。

## 何时使用

飞书群里观测云机器人 **@ 到本机器人**，消息体是告警通知。典型形态：

```
[严重] 2026-09-21 14:32:00 (+08:00) 订单同步失败率 > 5%  (r/3f8a2c)
查看相关日志：https://console.guance.com/...
```

**不适用**：人在群里口述报错、贴截图、给接口路径、提需求——那些走项目级分诊 skill。

## 流程

**0. 确认真的是告警**

按下述特征任一命中即认定，命中不了就别硬套：

| 特征 | 说明 |
|---|---|
| `(r/xxxxxx)` | 规则短 ID，六位十六进制 |
| `[严重] / [致命] / [错误] / [警告]` + 时间戳 | 告警级别行，时间戳通常带 `+08:00` |
| 「查看相关日志」/ console 链接 | 观测云控制台跳转 |

**1. 解析字段**

从告警正文抽出，能抽多少抽多少，抽不到就留空（**不要猜**）：

- **规则 ID + 规则名**：`r/xxxxxx` 与其后的人类可读标题
- **级别**：致命 / 严重 / 错误 / 警告
- **时间窗**：告警行的时间戳是**触发时刻**。取值区间按
  `[触发时刻 - 30min, 触发时刻 + 30min]` 展开；若正文含「首次触发/持续 N 分钟」，
  从**首次触发**延伸到当前。统一输出 ISO 8601 带时区：`YYYY-MM-DDTHH:MM:SS+08:00`
- **受影响对象**：接口路径、服务名、主机/IP、业务实体 ID（订单号、任务 ID 等）——正文里有什么拿什么
- **日志链接**：若有，原样保留

**2. 反查规则与触发日志（可选，有工具才做）**

这一步要拿到两样东西，**它们是下游分类的唯一依据**：

**a. 规则定义** —— 规则短 ID 只有观测云侧才知道完整定义（阈值、检测频率、聚合维度）。
按规则 ID 查，补全阈值与检测口径。

**b. 触发该规则的那条错误日志** —— 定位是哪条错误日志把这条规则打爆的，
摘出**原始错误文案**（错误码、异常类名、SQL 报错信息）。
下游要拿它做关键字分类，**摘要不够用，要原文**。

纪律：

- 工作区若提供观测云 CLI（`owl`）或等价通道 → 按上述两项查询
- **调 owl 前先 grep 本插件 `PITFALLS.md`**，看有没有该工具的已知坑（插件级约定）
- **工具不可用 / 查不到就如实标注**，把规则名原样带下去、日志字段留空。
  **绝不臆造阈值、绝不编造日志内容**——下游会拿它去 @ 人、建任务，编造等于误导

**3. 判断真伪**

这一步是本 skill 相对项目分诊**新增**的价值，用告警自身的信息就能判：

| 信号 | 倾向 |
|---|---|
| 同一规则 ID 在短时间内重复刷屏 | 持续型故障，不是抖动 |
| 级别=警告 且规则是资源类（CPU/内存/磁盘） | 先看是否自愈，可能无需人介入 |
| 时间集中在整点/发版前后 | 疑似发布或定时任务导致 |
| 日志链接可打开且能直接看到报错 | 直接采信，不必再查 |

判不了就**说判不了**，交给下游。本步禁止下"一定是 XX 导致的"这类结论——那是取证后的活儿。

**4. 交接**

输出下面的契约，然后交给项目分诊继续。**别自己往下走取证。**

## 输出契约

```
【观测云告警】
规则:   r/3f8a2c —「订单同步失败率 > 5%」
级别:   严重
时间窗: 2026-09-21T14:02:00+08:00 ~ 2026-09-21T15:02:00+08:00
受影响: /api/v1/orders/sync ｜ order-service
触发日志: <原始错误文案，供下游分类；查不到写「未定位」>
         例：OperationalError: (2006, "MySQL server has gone away")
真伪初判: 持续型故障（同规则 5 分钟内触发 4 次）
日志链接: <原样保留，若有>
```

交接句（照抄，别改写）：

> 若当前工作区存在项目级分诊 skill（如 `triage-issue`），把以上契约交给它继续；
> 若不存在，则按本 skill 收尾：给出真伪判断与归属倾向，并提示需人工补充项目上下文。

**为什么交接而不是自己查**：项目分诊 skill 是分流规则的**单一事实源**——它知道
该项目的服务划分、数据源、责任人映射。本 skill 重复实现那套，就是漂移的开始。

## 常见错误

| 错误 | 后果 |
|---|---|
| 把项目名/服务名/库名/人员写进本 skill | 通用性作废，换个项目就失效 |
| 工具不可用却"查到"了规则阈值或日志 | 编造证据，比没有证据更糟 |
| 解析完直接下根因结论 | 跳过取证，结论无据 |
| 主键/时间窗抽取时靠猜补空 | 下游查错对象 |
| 人在群里口述报错也走本 skill | 抢了项目分诊的触发 |
