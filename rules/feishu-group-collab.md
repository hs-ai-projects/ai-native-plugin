# 飞书群协作规则

## @ 回机制：谁 @ 你，回复就 @ 回谁

群里消息靠 @ 唤起对方——不 @ 的消息对方不会被唤起。因此任何回复一律 @ 回
发起者，不省略：

- 人类 @ bot → bot 回复必 @ 回那个人类。
- botA @ botB → botB 回复必 @ 回 botA。

被 @ 的一方回复时 @ 回，对话链才闭合；@ 发起方收到回复后醒来，结合对方回复
的内容判断下一步，三选一：

1. 还需要对方继续做 → 再 @ 对方，开启下一轮。
2. 自己能处理剩余 / 需转给别人（比如任务被拒，得转告人类原始发起人）→ 不
   @ 对方，独自继续处理。
3. 事情已经了结 → 结束，不再 @ 任何人。

**委派出去的任务，接收方完成时必须 @ 回委派方**——@ 是委派方得知"已完成"
的唯一通道，不 @ 对方不会醒来，任务完成与否无从知道。委派方收到"已完成"
后照上面三选一收尾（验收 / 续排 / 通知原始发起人后结束）。完成这一下 @ 回
和对话中每步回应必 @ 回一致，不可省略。

## 发协作消息：自然语言表明意图

发消息不套机器前缀，直接自然语言说清意图：

- 委派任务给另一个 agent → @ 对方，说清要对方做什么、为什么判定这事归对方。
  必须附上飞书任务链接（如果有任务 URL，对方点开看完整需求字段，不依赖转述）。对方
  完成时会按回声机制 @ 回你报"已完成"——这是必须的（见 @ 回机制节），否则
  你不会知道任务完成。委派时补一句完成后对方要做什么即可：验收后 merge / 告诉我（@回来） / 收到即了结，让对方知道要不要等你进一步指令。对方回应这笔委
  派（接受 / 拒绝 / 延后）的那一下同样必 @ 回。
- 回应另一个 agent 的委派（接受 / 拒绝 / 延后 / 已完成）→ 意图和理由说清，
  回复 @ 回委派方：接受 → 说"接手开工"；拒 / 延 → 带理由；已完成 → 带 MR
  链接。回应里可以带上你的**预期**——你希望对方下一步怎么走，给对方判断提供
  依据：拒 → 可说"请转告原始发起人"或建议改派给谁；延 → 可说"改期再派我"；
  已完成 → 可说"请验收"或"直接转发起人"。

## 收群消息：判意图

收到消息先按内容判断意图：

1. 委派请求 → 对方想请你处理一项任务。协作上你要
   做的是**回应委派方**：接受 / 拒绝 / 延后，回复 @ 回对方并带理由与预期
   （见发消息节"回应另一个 agent 的委派"条）。

2. 对你发出的委派的回应（对方已按 @ 回机制 @ 回你）→ 更新本地对该任务的
   认知，结合回复内容决定下一步（三选一）：
   - 接受 → 任务已转出，等对方最终"已完成"回报（回声必 @），或就此了结。
   - 拒 / 延 → 若有人类原始发起人，@ 回那个人转告"尚未处理"（不能让需求方
     以为已经在做）；没人则改派其他 agent 或结束。
   - 已完成 → @ 那个人一句结果。
